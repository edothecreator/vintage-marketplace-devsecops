 1. THE ONE THING THAT DECIDES THE GRADE
===============================================================================

 The brief states that priority goes to the quality of the cybersecurity
 approach, the automation of controls, and the ability to demonstrate the
 pipeline's effectiveness - rather than the number of features built.

 It then fixes the exact shape the demonstration must take:

   Security practice -> Tool -> Pipeline integration -> Detection
                     -> Result -> Corrective action

 Everything in this plan is organised backwards from that chain.
 Two consequences follow, and they drive the whole strategy.

 ---------------------------------------------------------------------------
 CONSEQUENCE 1 - A CLEAN APPLICATION PROVES NOTHING
 ---------------------------------------------------------------------------
 If our code is secure from the first commit, every scanner returns an empty
 report. An empty report demonstrates Detection -> Result -> Corrective action
 for exactly zero practices. We therefore need real findings.

 Section 9 defines a deliberate vulnerability programme to manufacture them
 under controlled conditions.

 *** THIS IS THE SINGLE MOST IMPORTANT TACTICAL DECISION IN THE PROJECT. ***

 ---------------------------------------------------------------------------
 CONSEQUENCE 2 - EVIDENCE MUST BE CAPTURED AS WE GO
 ---------------------------------------------------------------------------
 Pipeline run logs expire, branches get deleted, dashboards reset. Every phase
 below names the artefacts to save at the moment they are produced, into an
 evidence/ directory in the repository. Capture is part of each task's
 definition of done, not a task for the final week.

 3. ORDER OF ATTACK - AND WHY THIS ORDER
===============================================================================

 The sequencing is not arbitrary. Three rules govern it:

 1. PIPELINE SKELETON BEFORE APPLICATION CODE.
    If CI exists from day one, every later commit is scanned as it lands.
    Retrofitting security onto a finished app is the exact anti-pattern ASVS
    warns about - designing controls in afterwards costs far more than
    building them in from the start.

 2. THREAT MODEL BEFORE IMPLEMENTATION.
    P7 Threat modelling is a Tier 1 practice sitting in the Plan phase.
    Producing it after the code is written would be theatre, and the professor
    will be able to tell from the commit dates.

 3. DELIBERATE VULNERABILITIES LAST.
    We can only demonstrate detection once the detectors are wired up and the
    secure baseline exists to revert to.

 #   PHASE                                   EFFORT   PRACTICES SATISFIED
 --  --------------------------------------  -------  ----------------------
 0   Foundations & repository governance      2 days  P6 P9 P11 P15 P8
 1   Design, threat model, ASVS scoping       3 days  P7 P23 P24
 2   Backend & REST API                       6 days  P20
 3   Automated security test suite            4 days  P3
 4   Web front-end                            4 days  P20
 5   Pipeline security stages                 5 days  P1 P2 P4 P13 P30 P17
 6   Containerisation & deployment            3 days  P10 P12 P22
 7   Monitoring, logging, incident response   3 days  P5 P18 P28
 8   AI augmentation (app + pipeline)         4 days  LLM Top 10 + AI triage
 9   DELIBERATE VULNERABILITY DEMOS           4 days  Evidence for all above
 10  Pen test & performance analysis          3 days  P16 + required perf
                                                      analysis
 11  Report, documentation, defence rehearsal 4 days  P14 P31

 Effort figures are working days of focused effort, not calendar days.
 Compress by running phases 3-4 and 6-7 in parallel across team members.

 4. PHASE 0 - FOUNDATIONS & REPOSITORY GOVERNANCE
===============================================================================

 Cheap, fast, and it banks four Tier 1 practices before a single line of
 business logic exists.

 TASKS
   - Initialise repository; protect main: no direct pushes, require PR,
     require passing checks, require one approving review.          [P11]
   - Add CODEOWNERS so security-relevant paths require review.       [P9]
   - Minimal CI workflow: install, lint, build, run empty test suite. [P6]
   - Pre-commit hooks: Gitleaks for secrets, ESLint, formatter.  [P8][P30]
   - SECURITY.md and a decision log (docs/adr/) for architecture decisions.
   - evidence/ directory structure, one folder per practice.

 EVIDENCE TO CAPTURE
   - Screenshot of branch-protection settings (this IS the proof for P11).
   - First green pipeline run.
   - A commit deliberately containing a fake key, blocked by the pre-commit
     hook - terminal capture.

 5.3 ASVS SCOPING DECISION                                        [P24]
-------------------------------------------------------------------------------
 ASVS 5.0 defines three levels; L1 is roughly 20% of its ~350 requirements and
 L2 is what most applications should target.

 OUR DOCUMENTED DECISION:
   Full Level 1, plus targeted Level 2 on the chapters where a marketplace
   carries real risk:
     V2  Validation & business logic
     V4  API and web service
     V5  File handling
     V6  Authentication
     V8  Authorization
     V13 Configuration & secrets
     V16 Logging & error handling

   Chapters V10 (OAuth/OIDC) and V17 (WebRTC) are excluded as not applicable.
   ASVS explicitly encourages this kind of scoped fork, and the exclusion must
   be justified in the verification report.

 >>> WRITE THE JUSTIFICATION DOWN NOW.
     ASVS requires the verification report to state what was INCLUDED and to
     justify exclusions. If this document exists before implementation, the
     report writes itself at the end. If it does not, you will be
     reverse-engineering your own scope under deadline pressure.

 7. PHASE 3 - AUTOMATED SECURITY TEST SUITE                         [P3]
===============================================================================

 P3 is the third most-cited practice in the paper (56 publications) and is
 defined there as API, web application and unit testing with a security focus -
 DISTINCT from SAST and DAST.

 ASVS independently makes the point that running an off-the-shelf scanner is
 NOT the same as automated verification, and that application-specific checks
 must be written for anything involving business logic or access control.

 These two sources converge on the same deliverable, which is why this phase
 matters more than it first appears.

 Tooling: Jest + Supertest. Every test is named for the ASVS requirement it
 verifies. Minimum abuse cases:

 ABUSE CASE                                     EXPECTED       VERIFIES
 ---------------------------------------------  -------------  ----------
 Seller A edits seller B's listing              403            ASVS 8.2.2
 Buyer reads another buyer's order              403            ASVS 8.2.2
 Buyer calls admin moderation endpoint          403            ASVS 8.2.1
 Two concurrent orders, same unique item        one 201,       ASVS 2.3.4
                                                one 409
 Upload .png whose content is a script          400            ASVS 5.2.2
 Upload file above size cap                     413            ASVS 5.2.1
 Review body containing <script>                stored raw,    ASVS 1.3.1
                                                rendered inert
 Login brute force beyond threshold             429            ASVS 6.3.1
 Token with alg: none                           401            ASVS 9.1.2
 Expired token                                  401            ASVS 9.2.1
 Extra field role: admin in registration body   ignored        ASVS 15.3.3
 Prompt injection in AI description input       neutralised    LLM01

 >>> DOCUMENT THE GATE POLICY AS A DELIBERATE DECISION.
     "Fail the build on X, warn on Y" is itself a security decision and the
     professor may well probe it. Write the reasoning into an ADR: failing on
     every low-severity finding stops all work and teaches the team to bypass
     the pipeline; failing on nothing makes the pipeline decorative. The middle
     position needs stating, not assuming.

 9. PHASE 9 - DELIBERATE VULNERABILITY DEMONSTRATIONS
===============================================================================

 This is how the required six-step chain gets its evidence. Each demonstration
 lives on its own short-lived branch, is caught by exactly one named control,
 and is then fixed. Nothing vulnerable is ever merged to main.

 ID  INJECTED FLAW                 CAUGHT BY        PRAC.    CORRECTIVE ACTION
 --  ----------------------------  ---------------  -------  -----------------
 V1  String-concatenated SQL in    SonarQube        P1       Revert to
     the search query              (SAST)                    parameterised
                                                             Prisma query

 V2  Hard-coded API key in a       Gitleaks         P30      Move to secret
     config file                                             store, rotate key

 V3  Pin a dependency version      Dependency-      P13      Upgrade, re-scan
     with a known CVE              Check /          P4       clean
                                   Retire.js

 V4  Remove Helmet - CSP and       OWASP ZAP        P2       Restore headers,
     HSTS disappear                (DAST)                    re-scan

 V5  Delete ownership check on     Jest abuse-      P3       Restore
     PUT /api/listings/:id         case suite                middleware; add
                                                             regression test

 V6  Downgrade to an outdated      Trivy            P4       Return to patched
     Node base image                                         image

 V7  Concatenate raw user text     Prompt-          P3       Reinstate
     into the LLM prompt           injection test            sanitisation +
                                                             output encoding

 WHY V5 IS THE CENTREPIECE
   Broken access control is the hardest class for scanners to catch - ASVS says
   plainly that automated tools cannot fully verify business-logic and
   access-control requirements. Showing that YOUR OWN test suite catches an
   IDOR that SAST and DAST both miss demonstrates genuine understanding rather
   than tool installation.

   *** MAKE THIS THE FIRST DEMO IN THE ORAL DEFENCE. ***

 EVIDENCE PER DEMONSTRATION
   1. The injecting commit (diff).
   2. The failing pipeline run log, with the failing stage highlighted.
   3. The tool's report file, saved to evidence/<practice>/.
   4. The fixing commit (diff).
   5. The subsequent passing pipeline run.

 10. PHASE 10 - PENETRATION TEST AND PIPELINE PERFORMANCE ANALYSIS
===============================================================================

 The brief explicitly requires an analysis of the impact on pipeline
 performance, which is easy to forget and easy to score on.

-------------------------------------------------------------------------------
 10.1 MANUAL PENETRATION TEST                                      [P16]
-------------------------------------------------------------------------------
 Time-boxed manual pass with ZAP and Burp against staging, focused on what
 automation misses: authorization matrix across all three roles, order-flow
 sequencing, upload bypass attempts, and the AI endpoint.
 Output: a short findings report with severity and remediation status.

-------------------------------------------------------------------------------
 10.2 PERFORMANCE MEASUREMENT
-------------------------------------------------------------------------------
 Record mean wall-clock duration over at least five runs per configuration:

 CONFIGURATION                            MEAN DURATION   ADDED OVERHEAD
 ---------------------------------------  --------------  --------------
 Baseline: install, build, unit tests     to measure      -
 + SAST + secret scan                     to measure      to compute
 + SCA + dependency scan                  to measure      to compute
 + abuse-case suite                       to measure      to compute
 + image build + Trivy                    to measure      to compute
 + ZAP baseline scan                      to measure      to compute
 FULL SECURED PIPELINE                    to measure      TOTAL %

 Then document the optimisations applied and their effect:
   - dependency caching
   - parallel jobs
   - ZAP baseline on pull requests, full scan moved to a nightly schedule
   - SCA split between fast PR checks and deeper nightly analysis

 A pipeline that got slower and was then deliberately tuned is a far better
 story than one that was never measured.
